# Как проводим исследование

Сначала фиксируем билд, SHA-256, архитектуру, карту и ревизию инструментов. Затем выбираем одну задачу и различаем: факт по коду, наблюдение процесса, сообщение пользователя, гипотезу и отрицательный опыт.

Цепочка для сетевой механики: направление/opcode → decoder → handler → изменённое состояние → ответ → фактический эффект клиента. Название сигнала не доказывает структуру. Wire offset и native offset записываются отдельно. ASLR/RVA не смешиваются с адресом при базе0x140000000.

Использовали Python/struct/hashlib/unittest, адресный анализ PE и дизассемблирование, GDB hardware breakpoints, Proton/Wine, Xvfb/xdotool, выбранные UI-кадры, .NET8 для лобби, PowerShell для Windows. Ghidra применялась в некоторых исторических исследованиях; новый агент не должен запускать её автоматически. Извлечение ресурсов выполнялось отдельно, оригиналы не изменялись. Не нужны полные дампы для проверки конкретного getter.

Для динамического опыта: начальное состояние → одно действие → ожидаемое изменение → события и native/UI контроль → повтор/отрицательный контроль → cleanup и hash-check. Exit0, один пакет или UI-анимация сами по себе недостаточны. Proton и Windows отмечаем раздельно. Raw AUTH и ключи не публикуем; экспортируем выбранные игровые поля.

После опыта записываем `report.md`, безопасный `evidence.json`, команды проверок. Строку CSV меняем по устойчивому ID, сохраняем отрицательные результаты и следующий конкретный опыт. Этапы0/1/2 отражают критерии; величина прогресса считается весами10/15/15/20/20/20, а не субъективной оценкой. Историческая методика: [METHOD-HISTORY](docs/recovery/METHOD-HISTORY.md).
