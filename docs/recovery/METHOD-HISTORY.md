## Что именно считаем

Первичная инвентаризация содержит **114 пунктов**: **62** для минимальной зимней сессии (`core`), **48** расширений (`extended`), **4** исследовательских ветки (`research`). Вместе core+extended дают **110 задач целевого плана**. Это механики и необходимые задачи инфраструктуры, а не количество опкодов, предметов или строк кода.

Полный перечень всех механик оригинальной игры пока неизвестен. План описывает согласованную цель: вход → зимняя карта → движение и набор → лут/инвентарь → стрельба/броня/HP → зоны/погода → аирдропы → эвакуация → результат/повторная сессия; затем транспорт, боты, multiplayer и внешность. Другие карты, сезонные события, магазин, рейтинги и все варианты режимов не включены в знаменатель. Новые обнаруженные механики добавляются отдельными ID; реестр не объявляется полной спецификацией ROE.

`basis=observed` означает наличие наблюдений хотя бы по части задачи. `requirement` — цель восстановления, её существование/формат ещё не доказаны. `candidate` — пункт для сверки по ресурсам и целевому режиму: например, конкретные правила гранат, нокдауна и расходников нельзя считать установленными по одному знакомству с жанром. Требования пользователя хранятся отдельно в [описании матча](../match-rules-from-user-20261006.md); их приблизительные времена не заменяют найденные таблицы билда2022.

## Как получаются проценты

Каждая строка содержит шесть этапов. Значения: **0** — не подтверждено, **1** — частично/в ограниченном подмножестве, **2** — выполнен критерий этапа для всей указанной задачи.

| Колонка | Этап | Вес | Что необходимо для2 |
| --- | --- | ---: | --- |
| `contract` | Понятно действие и ожидаемый результат | 10% | Установлены условия, результат и существенные отрицательные случаи |
| `wire` | Установлены форматы/маршрут | 15% | Известны обязательные поля, направление, кодек и обработчик; для файловых входов — структура и потребитель |
| `data` | Установлены параметры/ресурсные входы | 15% | Известны необходимые таблицы/определения и их применимость к этой карте/задаче |
| `server` | Работает серверное состояние | 20% | Действие меняет нужное состояние; повтор и отказ не нарушают инварианты |
| `client` | Проверено применение клиентом | 20% | Нативный клиент отображает/использует ответ; для эксплуатационных задач проверен соответствующий стенд |
| `scenario` | Проверен весь сценарий задачи | 20% | Повторяемый полный цикл, отрицательный контроль и заявленные условия/платформы; нет открытого сбоя по критерию |

Формула строки: `progress_pct = Σ(вес_этапа × значение_этапа / 2)`.

Итог выбранного объёма: `Σ(progress_pct × weight) / Σ(weight)`. `weight=1/2/3/5/8` — **предварительная относительная сложность**, а не часы и не точность измерения. Такие задачи, как raycast, полный инвентарь и multiplayer, весят больше отдельного UI-ответа. В сводке отдельно считаются core и core+extended; research не повышает готовность игровой сессии. Подсчёт процентных пунктов точен по формуле, исходные оценки этапов/весов приблизительны.

Это **процент достигнутых этапов согласованного плана**, а не «восстановлено37% исходной игры» и не обещание оставшегося времени. Найденный формат получает часть баллов до реализации; полностью проверенная задача имеет100 и `status=verified`. Сейчас ни одна строка не объявлена полностью закрытой по строгим критериям: рабочие ограниченные сценарии отражены частичными этапами, а не обнулены.

`fidelity` учитывается отдельно от процента: `unknown` — исходное правило неизвестно; `diagnostic` — наша модель; `partial` — часть поведения связана с первичными источниками; `verified` — исходное правило доказано. Рабочий ответ с фиксированным уроном не становится исходной формулой урона. `confidence` — уверенность в записанных наблюдениях, а не вероятность завершить задачу или точность процента.

## Как вести прогресс после каждого опыта

1. Найти ID механики; при новом действии добавить строку, а не переписывать чужой ID. Отдельные предметы одного доказанного типа обычно входят в матрицу тестирования этой механики, не становятся тысячами новых строк.
2. Записать источник и собственный run: билд/SHA, направление и opcode, адрес/смещение, начальное состояние, действие, фактический результат. Сырые ключи/дампы/трафик в этот реестр не копировать.
3. Обновить `sources`, `evidence`, `primary_ref`, `limitations`, `acceptance`, `next_step`, `updated` и только подтверждённые этапы. Отрицательный опыт может уменьшить этап/процент; причину записать в журнал. Положительный опыт другого запуска не переносить на отрицательный.
4. Пересчитать `progress_pct` командой `--recalculate` и выполнить проверку. Если меняются состав, объём или веса плана, увеличить `plan_version` **у всех строк** и объяснить новый знаменатель. Изменения одного этапа версию плана не меняют.
5. Добавить датированную сводку и обновить progress/hypotheses, затем обновить копию в agents-context. Историю не переписывать. Git сохраняет остальные изменения описаний/приоритетов/зависимостей.

Из `ROE_SERVER/`, без игры, сервисов и дополнительных зависимостей:

```bash
# Только проверить CSV, ссылки, проценты и граф зависимостей; вывести сводку.
python -B tools/recovery_status.py

# Выдать контекст/инструкции только выбранным задачам; игра не запускается.
python -B tools/recovery_task.py --task 5-6

# Сохранить status.md и дописать историю этапов/доказательств отдельных механик.
python -B tools/recovery_status.py --recalculate --write --snapshot --note "MOVE02: 27 отдельно; таймер продолжает отсчёт, 2b ещё не проверен"
```

Текст note выше — пример будущего результата, не выполненный опыт. Каждая snapshot-команда добавляет три агрегата: core, target, research. В `updates.csv` при первом снимке записывается baseline каждой строки; далее добавляются только изменённые этапы/проценты/статусы/ссылки на опыт/ограничения и удалённые ID. Повтор снимка без изменений не создаёт дублей механик. Отдельные изменения плана сохраняются в Git. `history.csv` содержит SHA CSV, чтобы сопоставлять сводку с конкретным состоянием реестра.
