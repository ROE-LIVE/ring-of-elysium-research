# HP07: наблюдение после смерти, 2022

Состояние: 12.10.2026 01:22 UTC. EXE 0.2.989.0 x64, зимняя карта 16010, SHA-256 `2dca9b1e122e21363e14eeeb2372598c773205a907ed8d2b2d54a7229ad6ba18`. Правила наблюдения оригинального сервера для команд и режимов неизвестны. Реализована опциональная диагностическая опора.

## Первичный контракт

`0x6FBB`: S2C, тело 8 байт `>Q`, **Unit UID наблюдаемой сущности**, не Account UID соединения. Primary callback `0x140FD82A0` читает UID из decoded+4 и при gate `0x142D13C3E==1` вызывает `0x140FD6920`. Gate уже равен 1 у живых клиентов: его нельзя называть признаком смерти. Объект callback содержит указатель состояния по +0xC8; внутри byte+0 — active, Q+8 — текущий UID, Q+0x10 — запрошенный UID. Адресный разбор сохранён в HP06/selected-140fd6920-4704.asm, primary node содержит функцию по +0x18.

Нулевая цель очищает current/requested UID, **но active остаётся 1**. Это не завершение матча. При настоящей смерти `0x533` устанавливает Dead=1 в отдельном автомате жизни; предыдущая расшифровка приведена в отчёте HP06.

## Нативные проверки

267/268: адресные 1069 HP=0, 533, частный 106E и 6FBB отправлены только первому клиенту. Он наблюдает за живым вторым, второй остаётся Alive и active=0. Живой прошёл 927,84 см, удалённая модель — 936,96 см, конечная разница 3,85 см. Камера следует за моделью, видны `Spectating` и Report Spectating Player. Нажатие W у умершего не изменило XYZ, автомат оставался Dead=1. Прямые пакеты не меняли Python WorldState: эта проверка устанавливает только native-контракт.

269/270: отдельный летальный участок, hp_floor=0, death_on_zero=true, два серверных тика по 500. Настоящий WorldState достиг HP=0; сервер отправил 1069/533 и автоматически выбрал живого участника через **один 6FBB без 106E**. Первый: Dead=1, HP=0, world+0x21=1, observer active=1 и Unit2. Второй: Alive, observer active=0. После S на 2 секунды второй прошёл 650,33 см, модель — 685,87 см; конечное расхождение 35,64 см. Камера следует за ним. W умершего снова дал 0 см.

Затем второй вошёл в участок и умер. Сервер отправил первому 6FBB UID=0: native current/requested стали нулевыми, active остался 1. После позднего входа нового живого клиента 271 цель автоматически стала Unit3. Этот поздний вход — исследовательский контроль: правило запрета входа в уже закончившийся матч ещё не реализовано.

## Изменения и отрицательные случаи

`peer_spectator_2022.py` выбирает живую цель только в той же комнате, сохраняет текущую подходящую цель, меняет её после смерти/ухода, учитывает свежий authenticated transport и повторную доставку новому соединению. Флаг `--peer-spectator` требует shared-peer-health и по умолчанию отключён. Существующие серверные проверки действий умершего сохранены.

В live-команды добавлен необязательный recipient_actor_uid, отдельно от подстановки UID в тело. Причина: 265/266 получали общий untargeted 6FBB; здоровый 266 становился наблюдателем, поэтому старую попытку follow нельзя считать положительной. Адресность и атомарный отказ при неправильном UID покрыты тестами.

269/270 сначала имели неудачную начальную позицию/меню. До проверки урона выполнен ручной вход; координаты и Alive проверены отдельно. Попытка повторить 2B/27 через live JSON была отвергнута: ошибочное поле name вместо id, 1262 live_scene_error. Начальное положение восстановилось без этих команд; причинную связь с ними утверждать нельзя. Этот опыт не доказывает безошибочный холодный вход. Внешность и имя удалённого игрока — диагностический BE7-профиль.

404 исходных теста, 363 теста Windows-комплекта и verify-only прошли. Подтверждены Proton/loopback, не Windows/LAN. Оригинальные командные правила, выбор следующего игрока кнопкой, полный camera input и конечный результат комнаты остаются открытыми. Нулевой UID не заменяет отдельное событие окончания. Следующий пункт — EVAC04.

## Продолжающееся исследование камеры

271 после нулевой цели: UID и модель обновились, но камера осталась на прежнем месте. 272/273/274 повторили смерть/уход/поздний вход с двухсекундной задержкой выбора модели: тело появилось, затем при движении ушло из кадра; задержка не восстановила слежение. Это открытый переход после UID=0, а не положительный camera follow. Разница own/remote XYZ после S: 1,24 см, но совпадение координат модели не доказывает движение камеры. Первичная ветка 6FBE передаёт наблюдаемому игроку уведомление и формирует 6FC0; 6FBD имеет ветку сериализованных camera data. Следующий опыт — включить этот producer и установить адресный relay без угадывания полного 6FBA.
